# Changelog

## v1.2.0 (unreleased)

Go versions are released as git tags only; this entry tracks changes since v1.1.1.

### BREAKING
- Audience filters are now always evaluated with the client's `application` and `environment` names injected into the attribute map (system values first, user-set attributes overlaid on top), matching the collector, which already attaches both to every exposure server-side. This changes assignment for running experiments: a unit whose experiment has Audience enforced and an `environment`/`application` condition the client's values now satisfy (and which was not already satisfied by a user-set attribute of the same name) currently gets variant 0 (the condition never matched because the SDK did not supply those values), and after upgrading it gets randomised normally. Those experiments are broken today; this fixes them, but the assignment they produce changes. User-set attributes of the same name still win, including ones set after the context is created (the cached assignment is invalidated), and `app_version`/`application_version` are never injected. Nothing new is published: these values are not added to the publish payload.
- Users whose unit UID contains non-ASCII characters will be reassigned in running experiments: UIDs are now hashed from their UTF-8 bytes, as in the other SDKs. ASCII UIDs keep their assignments.
- Audiences are re-evaluated after `SetAttribute`/`SetAttributes`: a cached assignment whose audience result changes with the new attributes is recomputed, so a user can move in or out of an experiment's audience within one context.
- When several experiments define the same variable key, the value is read from the first experiment, by id, that the unit is assigned to or overridden in; `GetVariableValue` exposes each experiment visited, while `PeekVariableValue` exposes none (v1.1.1 used the last experiment in the payload). This matches the JS SDK's `_resolveVariableValue` rule and affects `GetVariableValue`, `PeekVariableValue`, `GetVariableKeys`, `GetVariableKeysAll` and `IndexVariables_`, all of which now follow experiment-id order.
- Go 1.20 or later is required (v1.1.1 built on Go 1.17). `resty` is pinned to v2.16.5.
- JSON custom fields parse any JSON value.
- Published exposures include `"ruleOverride"` (false unless an assignment rule chose the variant), as the JS SDK publishes it. Who moves: anyone comparing publish payloads byte for byte.
- Positional (unkeyed) struct literals of `jsonmodels.Experiment` and `jsonmodels.Exposure` no longer compile, because each gained public fields (`AssignmentRules`, `HoldoutIds` and the switchback fields, `RuleOverride`); `Assignment` gained `RuleOverride` too, and `jsonmodels.ContextData` gained `Holdouts`. Who moves: code building these with unkeyed literals, such as `jsonmodels.Exposure{1, "exp", ...}` or `jsonmodels.ContextData{experiments}`; switch to keyed literals (`jsonmodels.Exposure{Id: 1, Name: "exp", ...}`, `jsonmodels.ContextData{Experiments: experiments}`), which keep compiling. These fields carry the features on the wire and in the payload, so they cannot be private (holdout decisions themselves stay internal; `Assignment` is unchanged by holdouts). `ClientConfig`, `ContextConfig` and `ExperimentVariables` keep their v1.1.1 layout, and `jsonmodels.Experiment` keeps the standard `encoding/json` behaviour (no custom `UnmarshalJSON`), including when embedded in your own structs.

### Changed
- A `json.Number` value (from JSON decoded with `UseNumber`) is now a number in audiences and assignment-rule conditions: ordering, equality, truthiness, regex and string-`in` coercion, and semver use the JS numeric conversion rather than raw text; a literal beyond float64 is ±Infinity, as in JavaScript. Before, its string kind caused text comparisons. Who moves: customers setting `json.Number` attributes or using `UseNumber` in a custom `AudienceDeserializer`, whose conditions relied on raw text, exact digits beyond float64 precision, or non-empty zero text being truthy. Other attribute types are unchanged.
- Switchback experiments are now served by cluster and period. Before, this SDK ignored the switchback fields and served such an experiment as a unit experiment on its `unitType` (or not at all without one), which did not follow the schedule. Who moves: customers already running switchback experiments with this SDK; their units' variants and exposures change to the scheduled ones, and units without a cluster value stop publishing exposures.
- `SetData` and `SetDataFailed` called on a copy of the context (the value `WaitUntilReady` returns, or the one an event logger receives) now update the live context, as `Close`, `Publish` and `Refresh` on a copy already did; before, they replaced only the copy's data (the ready and failed flags were already shared). Who moves: code that relied on installing data into a copy without affecting the context it came from.
- `X-Agent` is now `absmartly-go-sdk/<version>` (`SDKName`, `SDKVersion`, `SDKAgent`, `Client.GetAgent`), instead of `absmartly-go-sdk`. The collector stores it verbatim, so it shows in exports. Who moves: dashboards or filters matching `agent = 'absmartly-go-sdk'` exactly.
- The context fetch (`GET /context`) now sends the same SDK headers as publish (`X-API-Key`, `X-Agent`, `X-Application`, `X-Environment`, `X-Application-Version`), as the JS SDK does on every request; previously it sent none.

### Added
- Switchback experiments (`Experiment.RandomizationType`, `SwitchbackClusters`, `SwitchbackClusterValues`, `SwitchbackStartAt`, `SwitchbackPeriodMs`, `SwitchbackCarryoverDurationMs`, `SwitchbackBurnInDurationMs`, `SwitchbackBurnOutDurationMs`, `SwitchbackDesignType`, `SwitchbackEstimand`; `jsonmodels.SwitchbackClusters`; `SwitchbackAssign` and `SwitchbackPermutation`), matching the Java SDK (#15) and the collector (R33): an experiment with `randomizationType` `"switchback"` is served by cluster and period instead of by unit. The linked unit types in `switchbackClusters` are read in their declared order (kept as decoded, never sorted); the first context unit whose attribute at the cluster path holds a non-empty string or a whole-number integer serves, and that raw value, unhashed, draws the variant for the period `floor((now - switchbackStartAt) / switchbackPeriodMs)` from the 64-bit seed. Every float (`3.0` included; `json.Number("3.0")` too), boolean, object, array, empty string and `nil` gives no cluster value. A value with its own JSON encoding (a struct, a JSON or text marshaler) is read from that encoding, as the collector reads the published attribute, so a whole `float64` struct field, encoded as `3`, keys a cluster. A string with invalid UTF-8 is keyed by its published text (each bad byte becomes U+FFFD), and an attribute that cannot be published (such as a `json.Number` that is not a number) gives no cluster value. An ineligible cluster (no value, disagreeing units, a value outside `switchbackClusterValues`), a draw before the start, and a schedule the collector cannot serve (no start, a start that is not hour aligned or outside `[0, 10000-01-01)`, a period of 0 or less, fewer than two arms) give variant `0` with no exposure; overrides, assignment rules, strict audiences, full-on, traffic (on the serving unit's hash) and custom assignments apply as for unit experiments. Holdouts never apply to a switchback. The cluster is read at the period's first read (a peek included); changing a cluster attribute mid-period, even before the exposure or a requeue, is not supported: the cached arm stays for the period and the change takes effect next period, as in the Java SDK and the collector. The exposure is published under the serving unit, once per period (two periods are kept per experiment), stamped with the clock reading that chose the period; exposure and publish payloads have no new fields. Carryover and burn windows and the estimand are carried, not used. A switchback field of the wrong type drops only that field. Payloads without switchbacks assign and publish exactly as before, and cached reads and exposures allocate as before; decoding one allocates as many times as before but more bytes, because the decoded experiment structs are wider (`jsonmodels.Experiment` gains 10 fields). An attribute value whose `MarshalJSON` or `MarshalText` calls back into the context deadlocks a switchback read, because cluster values are read under the context lock; such marshalers must not use the context.
- Holdouts (`ContextData.Holdouts`, `Experiment.HoldoutIds`, `jsonmodels.Holdout`), matching the JS SDK (#65) and the Java SDK: a unit held out by any holdout covering an experiment gets variant `0` and control values, and the experiment publishes no exposure of its own; arm 1 of a three-arm holdout (three values in its split, whatever its `holdoutType`) holds out only experiments that are not full-on. Overrides and matching assignment rules win over a holdout. Each covering holdout publishes one ordinary exposure per unit type (its id and name, the arm as `variant`) on the first `GetTreatment`/`GetVariableValue`, in holdout id order; peeks publish nothing. The arm is drawn with the covered experiment's unit and kept until the holdout's iteration changes. A holdout's id, iteration and seeds may be written as any integral number (`10`, `10.0`, `1e1`), as in JavaScript; holdouts with no split (absent, `null` or empty), unknown or non-numeric holdout ids, and unknown fields inside holdout entries are ignored (an entry with a `null` split is kept, as in the JS SDK, and covers nothing); a split element of `null` counts as `0`, as in JavaScript, but an entry whose split has an element that is a string, boolean, array or object is skipped as malformed (the JS SDK keeps it and coerces the element; the collector never sends one); a numeric seed is wrapped to 32 bits like the JS SDK's `setUint32`, and a non-numeric seed is `0` rather than coerced as JavaScript would; an experiment listing a holdout id twice is covered once, and a holdout id defined twice with definitions that draw different arms (iteration, seeds or split) covers nothing, and duplicates that draw the same arm count as one, so the result never depends on entry order (the JS and Java SDKs keep the last one; the collector never sends duplicates). Holdouts add no further publish fields for payloads without holdouts (the assignment-rule `ruleOverride` change above still applies). For an experiment a holdout covers (before or after the change), a read whose assignment a concurrent refresh or `SetUnit` replaces before the read claims its exposure exposes and returns the replacement instead, up to three attempts as in the Java SDK; only if every attempt is replaced again is the last one served without an exposure, as in Java. A claim already taken always commits, as in Java, so every read that served the claimed decision has it published. A variable read never takes a new exposure claim for an experiment the refresh removed or that no longer defines the key, and `QueueExposure` of an assignment replaced before it was claimed publishes nothing. Experiments no holdout covers keep the v1.1.1 exposure behaviour. Once a context has seen holdouts or assignment rules, an override that has not been exposed yet is resolved again when a refresh changes its experiment's id or iteration, so it serves and exposes the current definition's variables (the JS SDK keeps the cached values); an exposed override, and any override in a context with neither, keeps its cached values as before. Warmed cached reads and exposures add no allocations. Measured on a four-experiment payload without holdouts: context creation adds one allocation (222 to 223, about 2% slower), each assignment rebuild one (the retirement token), and decoding is about 9.5% more bytes in the same time, because the decoded and installed structs are a few bytes wider. Once a context has seen holdouts or assignment rules, each install (creation and every refresh) also records which variable keys each experiment defines, so a retried variable read never retains old variant values or other experiments' keys: about 14 more allocations and 7% more bytes per install on the same four-experiment payload with a holdout.
- Assignment rules (`Experiment.AssignmentRules`): ordered `assign` rules (a fixed variant) and `split` rules (percentages such as `20/30/50`, hashed with the experiment's own seed), limited by environment and by JSON-expression conditions. The first matching rule wins over the audience/`audienceStrict`, traffic, full-on and custom assignments; only `SetOverride` beats it. Exposures carry a new `ruleOverride` flag, so the collector leaves them out of analysis. A `split` that matches before its unit is set gives the experiment's no-unit result and is re-resolved once the unit is set, unless already exposed. Malformed rules are skipped in favour of the next rule, except that an applicable `assign` rule with an out-of-range variant (including an integral one too large for any experiment), or a `split` with a different number of values than the experiment has variants, stops rule evaluation and falls back to normal assignment without trying later rules (as in the JS SDK and the collector); a non-string or unparseable `assignmentRules` in the payload only drops that experiment's rules, without an error event. Unknown payload fields are ignored at every level. Matches the JS (#66) and Java (#17) SDKs.
- `semver_eq`, `semver_gt`, `semver_gte`, `semver_lt` and `semver_lte` JSON expression operators. Numeric operands are converted as the JS SDK does (`toFixed(15)`, trailing zeros dropped), so `1e-7` equals `"0.0000001"`; the other operators keep their formatting.
- `Client.WithApplicationVersion` and `Builder.ApplicationVersion`: sent as `X-Application-Version` when it is 1 to 18 digits, `"0"` otherwise (the collector reads it as a 64-bit integer and rejects other values). Previously always `"0"`. `Client.GetApplication`/`GetEnvironment`/`GetApplicationVersion`.
- Release workflow: pushing a `vX.Y.Z` tag that matches `SDKVersion` runs the tests and creates the GitHub release.
- `FinalizeAsync`, which also waits for logger delivery; `Finalize` event type alias (value `"Close"`).
- `GetCustomFieldValueE` (error-returning custom field access).
- `GetVariableKeysAll` returns every experiment per variable key; `GetVariableKeys` keeps returning the first one.
- `ErrContextClosed`, `ErrContextClosing`, `ErrContextNotReady`, with the v1.1.1 error texts. Read methods return `ErrContextNotReady` before the context is ready, with the same text as v1.1.1.
- `ErrUnitAlreadySet`, `ErrUnitBlank` and `UnitError`: unit errors keep the v1.1.1 texts (`unit already set`, `unit  UID must not be blank.`), match with `errors.Is`, and `UnitError.Canonical()` gives the cross-SDK text (`Unit '<type>' UID already set.`).
- `SetUnitValue` (string or number UIDs, numbers hashed as the rounded integer like JS), `GetUnit`, `GetUnits`, `GetAttribute`, `GetAttributes`.
- `HashUnitValue`, `UTF8Bytes`, `Base64UrlNoPadding` encoding helpers.
- `ContextPublisher_` field and `SetContextPublisher` (preferred over `ContextEventHandler_`).

### Fixed
- `SetOverride`/`SetCustomAssignment` are allowed after finalize, like the other SDKs.
- Exposure for an unknown experiment serializes `"unit": null` instead of `""`.
- The ready, error and refresh events are logged before `WaitUntilReady`/`Refresh` return.
- JSON expr: `eq` null handling, nested deep equality; `eq(null, null)` returns null.
- Close/flush/refresh: events kept pending on failed publish, concurrent `CloseAsync` callers share one future, no lost publishes, logger panics contained.
- Data races on `ReadyFuture_`, `RefreshFuture_`, `ClosingFuture_`, `RefreshTimer_`, `Timeout_` and `Attributes_`, and the `AttrsSeq` write during audience matching., and between a refresh writing `Index_` under `DataLock` and `GetTreatment`/`PeekTreatment` reading it (inherited from v1.1.1).
- A failed close no longer restarts the refresh timer. On success, `Close()` and an empty-queue `CloseAsync()` settle after the `Close` event is logged, as in v1.1.1.
- Builder `Timeout` applies to requests; the retry condition no longer panics on a nil response (502 and 503 are retried, as before).
