# Changelog

## v1.3.0 (unreleased)

Go versions are released as git tags only; this entry lists the changes since v1.2.0. v1.2.0 code keeps compiling and behaving as before, except for the changes listed under Changed. Every v1.2.0 struct keeps its layout, `jsonmodels.ContextData` and `jsonmodels.Experiment` included, so unkeyed (positional) literals that compiled against v1.2.0 still compile; holdouts and switchbacks travel in the new payload types below instead.

### Added
- `jsonmodels.ContextPayload` and `jsonmodels.ExperimentData`, the full context payload: `ContextPayload` holds `Experiments []ExperimentData` and the top-level `Holdouts`, and `ExperimentData` embeds the v1.2.0 `Experiment` and adds `HoldoutIds` and the switchback fields. Both decode from and encode to the collector's JSON. `ContextPayload.ContextData()` drops the new fields and `jsonmodels.PayloadOf(data)` lifts a `ContextData`. A context serves holdouts and switchbacks only from a `ContextPayload`, delivered by `Context.SetPayload`, `ABSmartly.CreateContextWithPayload`, `DefaultContextDataDeserializer.DeserializePayload`, `Client.GetContextPayload`, or a data provider implementing the new optional `ContextPayloadProvider` (`DefaultContextDataProvider` does: `CreateContext` and refreshes ask it for the payload, which the default client decodes with `DeserializePayload` when its deserializer implements the new optional `ContextPayloadDeserializer`). `GetContextData`, `Deserialize`, `GetData` and the `Ready` and `Refresh` events keep returning `jsonmodels.ContextData`, without the new fields; `SetData`, `CreateContextWith` and a provider or deserializer with only the v1.2.0 methods install exactly that, with no holdouts or switchbacks.
- Switchback experiments (`ExperimentData.RandomizationType`, `SwitchbackClusters`, `SwitchbackClusterValues`, `SwitchbackStartAt`, `SwitchbackPeriodMs`, `SwitchbackCarryoverDurationMs`, `SwitchbackBurnInDurationMs`, `SwitchbackBurnOutDurationMs`, `SwitchbackDesignType`, `SwitchbackEstimand`; `jsonmodels.SwitchbackClusters`; `SwitchbackAssign` and `SwitchbackPermutation`), matching the Java SDK (#15) and the collector (R33): an experiment with `randomizationType` `"switchback"` is served by cluster and period instead of by unit. The linked unit types in `switchbackClusters` are read in their declared order (kept as decoded, never sorted); the first context unit whose attribute at the cluster path holds a non-empty string or a whole-number integer serves, and that raw value, unhashed, draws the variant for the period `floor((now - switchbackStartAt) / switchbackPeriodMs)` from the 64-bit seed. Every float (`3.0` included; `json.Number("3.0")` too), boolean, object, array, empty string and `nil` gives no cluster value. A value with its own JSON encoding (a struct, a JSON or text marshaler) is read from that encoding, as the collector reads the published attribute, so a whole `float64` struct field, encoded as `3`, keys a cluster. A string with invalid UTF-8 is keyed by its published text (each bad byte becomes U+FFFD), and an attribute that cannot be published (such as a `json.Number` that is not a number) gives no cluster value. An ineligible cluster (no value, disagreeing units, a value outside `switchbackClusterValues`), a draw before the start, and a schedule the collector cannot serve (no start, a start that is not hour aligned or outside `[0, 10000-01-01)`, a period of 0 or less, fewer than two arms) give variant `0` with no exposure; overrides, assignment rules, strict audiences, full-on, traffic (on the serving unit's hash) and custom assignments apply as for unit experiments. Holdouts never apply to a switchback. A context that has seen a switchback checks variable reads against the installed experiment and rebuilds an unexposed override after an identity change, as one that has seen holdouts or assignment rules does (see Holdouts below); a switchback's unit identity is its generation, so an edit to its `unitType` alone affects neither its variable reads nor its cached slots. The cluster is read at the period's first read (a peek included); changing a cluster attribute mid-period, even before the exposure or a requeue, is not supported: the cached arm stays for the period and the change takes effect next period, as in the Java SDK and the collector. The exposure is published under the serving unit, once per period (two periods are kept per experiment), stamped with the clock reading that chose the period; exposure and publish payloads have no new fields. Carryover and burn windows and the estimand are carried, not used. A switchback field of the wrong type drops only that field, except the `switchbackClusterValues` allow-list: a value that is not an array, or an entry that is not a string, number or boolean, allows no cluster (the Java SDK ignores such an allow-list, or any allow-list with such an entry, and allows every cluster). A schedule number written as a JSON string (`"switchbackPeriodMs":"3600000"`) is dropped, where the Java SDK reads it as a number. The collector sends neither. A schedule number written with a fraction or exponent counts only when it is exactly integral (and at most 48 characters, with an exponent of at most 3 digits), and a repeated `switchbackClusters` key keeps its last value (a malformed earlier value does not make the map unreadable). Payloads without switchbacks assign and publish exactly as before, and cached reads and exposures allocate as before (nothing); a warmed switchback read allocates nothing either; decoding one allocates as many times as before but more bytes, because each decoded `ExperimentData` carries the 11 holdout and switchback fields. An attribute value whose `MarshalJSON` or `MarshalText` calls back into the context deadlocks a switchback read, because cluster values are read under the context lock; such marshalers must not use the context.
- Holdouts (`ContextPayload.Holdouts`, `ExperimentData.HoldoutIds`, `jsonmodels.Holdout`), matching the JS SDK (#65) and the Java SDK: a unit held out by any holdout covering an experiment gets variant `0` and control values, and the experiment publishes no exposure of its own; arm 1 of a three-arm holdout (three values in its split, whatever its `holdoutType`) holds out only experiments that are not full-on. Overrides and matching assignment rules win over a holdout. Each covering holdout publishes one ordinary exposure per unit type (its id and name, the arm as `variant`) on the first `GetTreatment`/`GetVariableValue`, in holdout id order; peeks publish nothing. On a shared variable key, as in the Java SDK, a suppressed experiment is not assigned, so it never wins the key; when no candidate wins, the first suppressed candidate supplies its control value (and its holdouts' exposures, but none of its own), and `GetVariableValue` fires the holdouts of every candidate it visits before the winner, since each was evaluated. The arm is drawn with the covered experiment's unit and kept until the holdout's iteration changes. A holdout's id, iteration and seeds may be written as any integral number (`10`, `10.0`, `1e1`), as in JavaScript; holdouts with no split (absent, `null` or empty), unknown or non-numeric holdout ids, and unknown fields inside holdout entries are ignored (an entry with a `null` split is kept, as in the JS SDK, and covers nothing); a split element of `null` counts as `0`, as in JavaScript, but an entry whose split has an element that is a string, boolean, array or object is skipped as malformed (the JS SDK keeps it and coerces the element; the collector never sends one); a numeric seed is wrapped to 32 bits like the JS SDK's `setUint32`, and a non-numeric seed is `0` rather than coerced as JavaScript would; an experiment listing a holdout id twice is covered once, and a holdout id defined twice with definitions that draw different arms (iteration, seeds or split) covers nothing, and duplicates that draw the same arm count as one, so the result never depends on entry order (the JS and Java SDKs keep the last one; the collector never sends duplicates). Holdouts add no further publish fields for payloads without holdouts (the assignment-rule `ruleOverride` change above still applies). For an experiment a holdout covers (before or after the change), a read whose assignment a concurrent refresh or `SetUnit` replaces before the read claims its exposure exposes and returns the replacement instead, up to three attempts as in the Java SDK; only if every attempt is replaced or made stale again is the last one served without an exposure, as in Java. A claim already taken always commits, as in Java, so every read that served the claimed decision has it published. A variable read never takes a new exposure claim for an experiment the refresh removed or that no longer defines the key (it moves on to the next experiment defining the key), and a decision that is no longer current by the same validation a cached read applies (experiment identity, full-on variant, traffic split, covering holdout iterations, overrides, rules and audience) is resolved again and the current one served and exposed instead, and `QueueExposure` of an assignment replaced before it was claimed publishes nothing. Experiments no holdout covers keep the v1.1.1 exposure behaviour. Once a context has seen holdouts or assignment rules, an override that has not been exposed yet is resolved again when a refresh changes its experiment's id, iteration or unit type, so it serves and exposes the current definition's variables (the JS SDK keeps the cached values); an exposed override, and any override in a context with neither, keeps its cached values as before. In such a context a decision that has not been exposed yet is also resolved again when a refresh edits its audience expression or strictness (the JS and Java SDKs never compare the audience definition; they re-evaluate the expression only after an attribute changes); an exposed one keeps its cached decision. Warmed cached reads and exposures add no allocations; the first exposing variable read in a context that has seen holdouts or rules makes two more (48 B), for the claim check. Measured against v1.2.0 on a four-experiment payload without holdouts or switchbacks (`sdk/testAssets/context.json`): `Deserialize` makes one more allocation (96 instead of 95) with about 64% more bytes (9.8 KB instead of 6.0 KB) and is about 3% slower, because it decodes the full payload and then copies out the `ContextData`, and `CreateContextWith` makes the same 224 allocations with about 2% more bytes and about the same time; each assignment rebuild makes one more allocation (the retirement token). Once a context has seen holdouts or assignment rules, each install (creation and every refresh) also records which variable keys each experiment defines, so a retried variable read never retains old variant values or other experiments' keys: about 14 more allocations and 7% more bytes per install on the same four-experiment payload with a holdout.

### Changed
- A `json.Number` value (from JSON decoded with `UseNumber`) is now a number in audiences and assignment-rule conditions: ordering, equality, truthiness, regex and string-`in` coercion, and semver use the JS numeric conversion rather than raw text; a literal beyond float64 is ±Infinity, as in JavaScript. A `json.Number` haystack in `in` is a number, so its digits are not searched as text, as with a `float64`. Before, its string kind caused text comparisons. Who moves: customers setting `json.Number` attributes or using `UseNumber` in a custom `AudienceDeserializer`, whose conditions relied on raw text, exact digits beyond float64 precision, or non-empty zero text being truthy. Other attribute types are unchanged.
- Switchback experiments are now served by cluster and period when the context is given a `ContextPayload` (the default client path). Before, this SDK ignored the switchback fields and served such an experiment as a unit experiment on its `unitType` (or not at all without one), which did not follow the schedule. Who moves: customers already running switchback experiments with this SDK; their units' variants and exposures change to the scheduled ones, and units without a cluster value stop publishing exposures.
- Switchback serving and holdouts need the payload path (see `ContextPayload` above). The default client, deserializer and provider take it, so `CreateContext` and refreshes serve them with no code change. A custom `ContextDataDeserializer` or `ContextDataProvider` with only the v1.2.0 methods, and data passed to `SetData` or `CreateContextWith`, still give a context without them, which serves a switchback experiment as a unit experiment and ignores holdouts, as v1.2.0 did. Who moves: customers with a custom deserializer or provider, or who prefetch data, who want holdouts and switchbacks served; implement `DeserializePayload` or `GetContextPayload`, or use `SetPayload`/`CreateContextWithPayload`.

## v1.2.0 (unreleased)

Go versions are released as git tags only; this entry lists every change since v1.1.1. v1.1.1 code keeps compiling and behaving as before, except for the changes listed in these notes: Changed lists the intended behaviour changes, and some entries under Fixed also change what callers see (for example, `Publish()` returns the publish error where v1.1.1 returned nil). Two of the Changed entries affect source or JSON compatibility: unkeyed (positional) literals of `jsonmodels.Experiment` and `jsonmodels.Exposure` no longer compile, and customer structs that embed `jsonmodels.Exposure` are encoded by its new `MarshalJSON`. Exported names that existed only on unreleased main after v1.1.1, and were never in a tagged release, are not in v1.2.0: `Context.AudienceMatches`, the `Context` fields `AttrsSeq_`, `StateLock_` and `FinalizedFuture_`, the `Assignment` fields `RuleOverride` and `AttrsSeq`, `ABSmartly.ContextPublisher_`/`ABSmartlyConfig.ContextPublisher_` (use `ContextEventHandler_`, as in v1.1.1, or the builder's `ContextPublisher`) and `DefaultVariableParser.ParseCustomFieldValue`. Leaving them out keeps v1.1.1's struct layouts and method sets (a test checks the value and pointer method sets of every exported v1.1.1 struct type against the published v1.1.1); code built against main that uses them needs changing. They remain on `next/major` for the next major version. Requires Go 1.17 or later. That is v1.1.1's real floor: its go.mod said `go 1.15`, but it used `atomic.Value.CompareAndSwap` and did not build before Go 1.17.

### Added
- Assignment rules (`jsonmodels.Experiment.AssignmentRules`): ordered `assign` rules (a fixed variant) and `split` rules (percentages such as `20/30/50`, hashed with the experiment's own seed), limited by environment and by JSON-expression conditions. The first matching rule wins over the audience/`audienceStrict`, traffic, full-on and custom assignments; only `SetOverride` beats it. A `split` that matches before its unit is set gives the experiment's no-unit result and is re-resolved once the unit is set, unless already exposed. Malformed rules are skipped in favour of the next rule, except that an applicable `assign` rule with an out-of-range variant, or a `split` with a different number of values than the experiment has variants, stops rule evaluation and falls back to normal assignment (as in the JS SDK and the collector). A non-string or unparseable `assignmentRules` only drops that experiment's rules. Rules are decoded as standard JSON, independently of a custom `AudienceDeserializer`, which is never called for them. Matches the JS (#66) and Java (#17) SDKs.
- `semver_eq`, `semver_gt`, `semver_gte`, `semver_lt` and `semver_lte` JSON expression operators. Numeric operands are converted as the JS SDK does (`toFixed(15)`, trailing zeros dropped), so `1e-7` equals `"0.0000001"`.
- `NewBuilder()` (`ABsmartlyBuilder`), with `ApplicationVersion`, `Timeout`, `Retries` and the other options; `ABsmartly`/`ABsmartlyConfig` aliases of `ABSmartly`/`ABSmartlyConfig`.
- `Client.WithApplicationVersion`, sent as `X-Application-Version` when it is 1 to 18 digits and `"0"` otherwise (the collector reads it as a 64-bit integer). `Client.GetApplication`, `GetEnvironment`, `GetApplicationVersion`, `GetAgent`.
- `SDKName`, `SDKVersion`, `SDKAgent`.
- `Context.FinalizeAsync`, which also waits for logger delivery; `Finalize` event type alias (value `"Close"`).
- `Context.GetCustomFieldValueE` (error-returning custom field access) and `CustomFieldValueParser`, an optional interface a custom `VariableParser` can implement to parse `json` custom fields.
- `Context.GetVariableKeysAll` returns every experiment per variable key; `GetVariableKeys` keeps returning one.
- `ErrContextClosed`, `ErrContextClosing`, `ErrContextNotReady`, `ErrUnitAlreadySet`, `ErrUnitBlank` and `UnitError`, for `errors.Is`/`errors.As`. The error texts are unchanged from v1.1.1; `UnitError.Canonical()` gives the cross-SDK text (`Unit '<type>' UID already set.`).
- `Context.SetUnitValue` (string or number UIDs; numbers hashed as the rounded integer, like JS), `GetUnit`, `GetUnits`, `GetAttribute`, `GetAttributes`.
- `HashUnitValue`, `UTF8Bytes`, `Base64UrlNoPadding` helpers; `TypeError`; `future.PanicError`.
- Release workflow: pushing a `vX.Y.Z` tag that matches `SDKVersion` runs the tests and creates the GitHub release.

### Changed
These follow the cross-SDK contract agreed for all ABsmartly SDKs in 2026-11; each says who is affected.
- Audiences and assignment-rule conditions see the client's `application` and `environment` names as attributes (system values first, user-set attributes of the same name win). `app_version` is never injected and nothing new is published. Who is affected: experiments with an enforced audience on `application`/`environment` that no user attribute satisfied; those units got variant 0 and are now randomised normally.
- Audiences are re-evaluated after `SetAttribute`/`SetAttributes`: a cached assignment whose audience result changes is recomputed. Who is affected: code that sets attributes after reading a treatment; a strict audience can move the unit from variant 0 to its assigned variant, with a second exposure. A custom `AudienceDeserializer` is therefore called again for the revalidated experiment (see Fixed).
- Shared variable keys: when several experiments define the same key, `GetVariableValue`/`PeekVariableValue` follow the rule described under Fixed: the first experiment, by id, that the unit is assigned to, overridden in or rule-assigned to wins, and only it is exposed. `GetVariableKeys`, `GetVariableExperiment`, `GetVariableAssignment` and `IndexVariables_` use the lowest-id experiment. v1.1.1 used the last experiment in the payload. On a context the SDK created, a key defined by a single experiment follows the same rule: a unit that is not assigned to it (its unit type is not set, or it is outside a strict audience) gets the caller's default instead of variant 0's value, as in the Java SDK; a `Context{...}` literal keeps v1.1.1's behaviour. Who is affected: payloads where two experiments share a variable key, and code that read variant 0's variable values for unassigned units.
- Published exposures always include `"ruleOverride"` (false unless a rule chose the variant), and an exposure for an unknown experiment publishes `"unit": null` instead of `""`, as the JS SDK does. Who is affected: anyone comparing publish payloads or `Exposure` event JSON byte for byte.
- `X-Agent` is `absmartly-go-sdk/1.2.0` instead of `absmartly-go-sdk`. The collector stores it verbatim, so it shows in exports. Who is affected: dashboards or filters matching `agent = 'absmartly-go-sdk'` exactly.
- The context fetch (`GET /context`) sends the SDK headers (`X-API-Key`, `X-Agent`, `X-Application`, `X-Environment`, `X-Application-Version`), as the JS SDK does on every request; v1.1.1 sent none. Who is affected: proxies or mocks that reject unexpected headers on the GET.
- `jsonmodels.Experiment` gained `AssignmentRules` and `jsonmodels.Exposure` gained `RuleOverride`, the wire fields of assignment rules. Who is affected: code building these two payload models with unkeyed literals (`jsonmodels.Exposure{1, "exp", ...}`); keyed literals keep compiling. No other v1.1.1 struct changed layout; `sdk.Context` keeps its 36 v1.1.1 fields.
- `Exposure` events and published exposures write an empty unit (an unknown experiment's) as `"unit": null` instead of `""`, through a `MarshalJSON` method on `jsonmodels.Exposure`, as the JS SDK does. Because the method encodes with `json.Marshal`, HTML characters in an exposure are always escaped (`<` becomes `\u003c`), even with `Encoder.SetEscapeHTML(false)`. Who is affected: customer structs that embed `jsonmodels.Exposure` and are encoded with `encoding/json` (the embedded method encodes them, so their own fields are left out; use a named `Exposure` field instead), and code that encodes exposures with HTML escaping turned off.
- A value copy of a context the SDK created (`copied := *ctx`, `WaitUntilReady()`'s result, or the `Context` an event logger receives) acts on the original context: `SetAttribute`, `SetUnit`, `Track`, `Publish`, `Refresh` and `Close` through the copy change the original, and reads through it see the original's attributes, units, assignments and data (`GetExperiment` and `GetVariableExperiment` through a copy of a context whose `Clock_` was replaced read the copy's own `Index_`, as in v1.1.1, which `SetData`, `SetDataFailed` and `Refresh` through that copy, including a `Refresh` that joins one already running, keep current when the call returns, even if an event logger refreshed again meanwhile). In v1.1.1 `SetAttribute` through a copy appended to the copy's own attribute slice, so the original never saw it (units, events and locks were already shared). Who is affected: code that copied a context to keep a separate set of attributes; create a separate context instead. A `Context{...}` literal still acts on its own fields.
- `Context.Index_`, `IndexVariables_` and `AssignmentCache` keep their v1.1.1 types and are still filled, but a context created with `CreateContext` reads its own private index and cache, so writing these fields no longer changes its assignments or variable lookups (a `Context` built as a literal still reads `Index_`). Who is affected: code that edited them directly to inject experiments or cached assignments; use `CreateContextWith`, `SetOverride` or `SetCustomAssignment`.
- `Context.Clock_` of a context the SDK creates (`ABSmartly.CreateContext`/`CreateContextWith`, or the package `CreateContext`) is a private clock wrapping the SDK's default clock, or the clock passed to the package `CreateContext`, and delegates `Millis()` to it. So `ctx.Clock_` no longer equals or type-asserts to that clock, and `Assigners_` holds one private entry besides the `*VariantAssigner` values keyed by unit type. Replacing `ctx.Clock_` still works as in v1.1.1: the context keeps its state and uses the new clock, and assigning one context's `Clock_` to another only shares the clock. Who is affected: code that compares or type-asserts `Context.Clock_`, or ranges over `Assigners_` asserting every value is a `*VariantAssigner`.
- Unit UIDs with non-ASCII characters are hashed from their UTF-8 bytes, as in the other SDKs; v1.1.1 dropped every non-ASCII character, so different UIDs collided. Who is affected: units with non-ASCII UIDs are reassigned in running experiments; ASCII UIDs keep their assignments.
- `SetOverride` and `SetOverrides` succeed after `Close`, like the other SDKs; v1.1.1 returned the closed error. `SetCustomAssignment`/`SetCustomAssignments` still return it. Who is affected: code relying on the error from `SetOverride`.
- The module requires `github.com/go-resty/resty/v2` v2.16.5 (v1.1.1: v2.7.0), which keeps the Go 1.17 floor. Who is affected: modules pinning an older resty, which Go's minimal version selection raises.
- A default context-data decode that fails for a released field returns the same error text as v1.1.1, but an `*json.UnmarshalTypeError` reports its Go `Type` from an internal compatibility model. Who is affected: code that inspects that error with `errors.As` and compares its `Type`; code comparing `err.Error()` is unaffected.
- `json` custom fields with the default parser return any JSON value (array, string, number, boolean) instead of only objects (cross-SDK scenarios 53-58); JSON `null` and invalid JSON still return a nil `map[string]interface{}`. Who is affected: code type-asserting every `json` custom field to `map[string]interface{}`.

### Known issues
- On a context whose `Clock_` was replaced, or one built as a `Context{...}` literal, each read finds the context's private state under that context's exclusive `ContextLock_`, so concurrent readers of the same context serialise; a literal also compares the read experiment's `Index_` entry with its private copy on each read. Contexts made with `CreateContext` and left with their clock are unaffected.

### Fixed
- Shared variable keys: the key now resolves to one winner, and only experiments the unit is in are exposed. v1.1.1 read and exposed only the last experiment in the payload that defined the key, whether or not the unit was assigned to it. Unreleased main (never tagged) instead exposed every experiment it visited while looking for the key, so a unit not assigned to a lower-id experiment (outside its strict audience, or without a unit of its type) was still recorded in it, and when the winner's variant did not define the key it fell through to a later experiment, biasing both experiments by arm. Who is affected: anyone running two or more experiments that define the same variable key; and, for a key only one experiment defines, code reading it for units that experiment does not assign (outside a strict audience, or without a unit of its type): v1.1.1 queued an exposure with `assigned: false` for them, and v1.2.0 queues none. The rule now applied, matching the Java SDK: the candidates are the experiments any of whose variants define the key, in experiment-id order; the winner is the first candidate the unit is assigned to, overridden in or rule-assigned to; its selected variant supplies the value, and when that variant does not define the key the caller's default is returned (a key defined as `null`, `false`, `0` or `""` is a value, not missing). Only the winner is exposed; with no winner the default is returned and nothing is exposed. `PeekVariableValue` resolves the same way and exposes nothing. A unit outside a strict audience is not assigned, so it reads the default and is not exposed.
- A custom `AudienceDeserializer` is never called while the context holds a lock. It is not called when an override or a matching assignment rule decides the variant; it can now call context methods from inside (except reading the experiment whose audience it is parsing, which deadlocked in v1.1.1 and now recurses); on unreleased main a deserializer calling back into the context (`QueueExposure`, `Track`, `WaitUntilReady`, `Publish`, `Refresh`) hung. The built-in deserializer's parses are cached per audience text, so it is not called again for cached reads, attribute changes or a refresh with unchanged audience text (two reads that both miss the cache at the same moment may each parse the text). A custom deserializer is called for every audience evaluation, as in v1.1.1: at the experiment's first assignment and, new in this release, again when an attribute or rule change revalidates a cached assignment (the assignment, and so its exposure, is kept when the outcome is unchanged). Its result is used immediately and never kept. Within one context, a custom audience's decode and the evaluation of its result are serialised as in v1.1.1. A deserializer may call back into the context. Reads made on its own goroutine (including a logger reporting its panic), or by a `Refresh`, `WaitUntilReady`, `Publish` or `Close` it is waiting on (that operation's event loggers and variable parser, and any `Refresh` or `Publish` they wait on in turn), run nested and may call the deserializer again. Those nested decodes happen before the outer deserializer returns, so a deserializer that reuses its result storage across its own nested calls is responsible for that storage, as with any reentrant call. Reads from any other goroutine, independent event loggers included, wait for the parse in progress, as in v1.1.1, so a deserializer that reuses its result storage between calls is otherwise safe on one context. Because the `Refresh` and `Ready` events are now logged before `Refresh`/`WaitUntilReady` return, such a logger's read always decodes inside the deserializer's call that is waiting (in v1.1.1 the `Refresh` and `Ready` events were logged after `Refresh` and `WaitUntilReady` returned, so their reads decoded after that result was evaluated). Only `Refresh`, `WaitUntilReady`, `Publish` and `Close` lend: a deserializer that waits on a `RefreshAsync`, `WaitUntilReadyAsync`, `PublishAsync` or `FinalizeAsync` future itself deadlocks if that operation's logger or parser reads a custom audience of the context. Across contexts sharing a deserializer it must be safe for concurrent use, as in v1.1.1 where one deserializer served all contexts. Replacing `AudienceMatcher_` takes effect at the next evaluation. If new data with a changed audience is installed during every parse of a read, the read gives up after 4 parses and ignores that audience, as for an unparseable one; the assignment it builds is cached like any other, and the next attribute, rule or experiment change parses the audience again. A failed parse (an error, a panic, or a document without a map/list/array filter) is not shared: the audience is ignored for that evaluation, and another experiment with the same audience text asks the deserializer again, as v1.1.1 parsed on every assignment. An assignment built with the audience ignored keeps that outcome, without asking the deserializer again on attribute or rule changes, until the experiment run (id or iteration), its audience text or the deserializer changes (for a deserializer that cannot be compared with `==`, such as a func adapter or a struct holding one, or one that is not equal to itself, only a change of type counts). A parse that fails while revalidating a cached assignment is only recorded when ignoring the audience changes the outcome, which rebuilds the assignment as above; when the outcome is unchanged the assignment is kept as is and the next revalidation asks the deserializer again. A `Context{...}` literal picks up an edited `Index_` entry at its next read, as in v1.1.1, without taking `DataLock`; an edited entry keeps assignment rules installed by `SetData` only while its `assignmentRules` text is unchanged. Value copies of a literal share its private index, so a copy given new data with `SetData` and the original's own `Index_` entry overwrite each other's rules: give each copy its own data by building a separate literal.
- A panic in a custom `AudienceDeserializer` while it parses an audience is logged as an `Error` event and the audience is treated as unparseable and ignored, as v1.1.1 does when the deserializer returns an error, instead of escaping from the treatment read as in v1.1.1. During that error event, a logger can read the same experiment without recursively calling its deserializer; a different experiment with the same audience text, including a replacement installed under the same name with a new id or iteration, still parses independently. A `panic(nil)` counts as a panic on every supported Go version.
- `Publish()` returns the publish error instead of nil, and a failed publish keeps the events queued for the next publish instead of dropping them.
- A failed `Close()` leaves the context open with its events queued and can be retried; the `Close` event is logged only on success, and the refresh timer is not restarted. On success, `Close()` and an empty-queue `CloseAsync()` settle after the `Close` event is logged. Concurrent `CloseAsync` callers share one future, and in-flight publishes are waited for.
- Exposures are no longer queued on a closed context.
- `Refresh()` on a closed context returns instead of panicking; a refresh that finishes after close does not restart the timer.
- The ready, error and refresh events are logged before `WaitUntilReady`/`Refresh` return.
- `SetUnit` with the same UID plus surrounding spaces no longer returns `unit already set`.
- Panics no longer crash the host: transport errors in `GetContextData`, a non-resty response from a custom `HTTPClient`, a data provider or publisher returning no future or panicking, a negative override, a nil `AudienceMatcher` deserializer, event logger panics, and JSON expressions on empty maps, maps without `path`, uncomparable values or sized number types.
- JSON expressions: `eq` null handling, deep equality for arrays and maps (independent of key order), `eq` on `int64`/`uint`/`float32` attributes, and sized numbers in boolean context.
- Data races on `ReadyFuture_`, `RefreshFuture_`, `ClosingFuture_`, `RefreshTimer_`, `Timeout_`, `Attributes_` and `Index_`, and a race in `future.Future.Listen` that could drop a callback; `Future.Join` no longer runs callbacks twice.
- Builder `Timeout` applies to requests; the retry condition no longer panics on a nil response (502 and 503 are retried, as before). TLS 1.2 is the minimum version.
